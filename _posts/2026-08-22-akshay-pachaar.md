# CAG vs RAG: как перестать стрелять по кошельку запросами к векторной базе

Каждый раз, когда ваш RAG-бот лезет в векторную базу за одними и теми же документами — вы сжигаете деньги и время. Документация, которую не трогали год, политики компании, справочники — всё это пересчитывается при каждом запросе. Cache-Augmented Generation (CAG) обещает решить эту проблему радикально: загрузить статичные данные один раз и забыть про них.

## В чём суть

RAG хорош для динамической информации, которая часто обновляется. Но для статичного контента это расточительство: модель каждый раз заново прогоняет через себя километры текста, который не менялся месяцами.

CAG работает иначе. Статичные данные загружаются в KV-память модели один раз — при инициализации контекста. Дальше модель использует предвычисленный кеш. Никаких повторных обращений к векторной базе, никаких лишних токенов в промпте.

Механизм простой: языковые модели строят KV-кеш для каждого токена. Если промпт совпадает байт в байт с предыдущим — модель не перевычисляет, а берёт результат из кеша. OpenAI и Anthropic уже поддерживают это в своих API через prompt caching.

## Как это работает на практике

Схема такая: статичные данные — в CAG-кеш, динамические — в RAG-поиск. Комбинация даёт максимальный эффект:

- **Холодные данные** (документация, политики, справочники) — один раз загрузили и всё
- **Горячие данные** (последние записи, изменения, актуальные срезы) — достаём через векторный поиск

Результат: скорость inference растёт, счета за API падают. Если вы каждый день дёргаете одни и те же документы — экономия будет ощутимой.

## Подводные камни, о которых молчат

Есть нюанс, который превращает эйфорию в головную боль: кеш работает только при **точном совпадении префикса**. Переставьте два документа местами — оба кеша промахнутся. Закешировали A, потом B, а затем запросили оба — второй документ окажется мимо, потому что порядок меняет контекст.

Это означает, что:

- Структура кешируемых данных должна быть фиксированной
- Любое изменение порядка или состава — полный пересчёт
- Нужно чётко разграничивать, что идёт в кеш, а что — в поиск

## Когда это стоит использовать

CAG + RAG — это не серебряная пуля. Это инструмент для конкретных сценариев:

**Идеально подходит:**

- Чат-боты по внутренней документации
- Системы политик и регламентов
- Справочные системы с редко меняющимся контентом
- Любые приложения с повторяющимися запросами к одним и тем же текстам

**Не стоит использовать:**

- Для данных, которые часто обновляются (кеш придётся перестраивать)
- Если не можете гарантировать фиксированный порядок документов
- Когда статичных данных слишком много и они не влезают в контекст

## Практический совет

Не гонитесь за максимизацией кеша. Переполните контекст — и модель начнёт тормозить вместо того, чтобы ускоряться. Выбор кэшируемых данных должен быть строгим: только статичное, только ценное, только то, что меняется редко.

Оставьте RAG для динамики, CAG — для статики. Разделите зоны ответственности, и ваш inference ускорится, а счета за API приятно удивят.
