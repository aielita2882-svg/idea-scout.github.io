Интеграция AI-агентов с GLPI через MCP: Безопасность превыше всего

Большинство попыток подружить LLM с корпоративными ITSM-системами заканчиваются либо в read-only режиме, либо кошмаром при аудите прав доступа. Нашел интересный проект — MCP-клиент на Python для GLPI 10.0.17, который решает проблему «галлюцинаций» агента на уровне архитектуры.

Технический стек и архитектура

Проект реализует Model Context Protocol (MCP), предоставляя агенту доступ к API GLPI. Главная фишка — жесткая изоляция операций записи.

Цифры по инструментам:

  • Всего: 77 MCP-инструментов.
  • Read-only: 22 инструмента (доступны по умолчанию).
  • Write-операции: 55 инструментов (скрыты за feature-флагами).

Система работает по принципу Explicit Allow. Чтобы агент мог создать тикет или добавить вложение, соответствующий флаг должен быть явно включен в конфиге. Это исключает сценарии, когда агент случайно удаляет базу тикетов или меняет статус всех заявок на «Закрыто» из-за неверного промпта.

Ролевая модель и управление доступом

Вместо того чтобы давать агенту общий API-токен с широкими правами, внедрены профили:

  1. Tasker: Минимальный набор прав для базовых операций.
  2. Supervisor: Расширенный профиль. Протестированы сценарии создания тикетов, добавления комментариев с вложениями, согласований и управления задачами.

При этом критические разделы — управление группами, активами, модули Problem и Change — закрыты по умолчанию. Это позволяет реализовать принцип наименьших привилегий (PoLP) на уровне инструментов AI.

Работа с файлами и валидация

Обработка вложений реализована с параноидальным подходом к безопасности:

  • Лимиты: Один файл до 2 MiB, общий пакет до 10 MiB.
  • Фильтрация: Проверка идет по расширению, MIME-типу и сигнатуре файла.
  • Blacklist: WebP, .py, .sql, .parquet блокируются на стороне клиента, не доходя до API GLPI.
  • Целостность: В новый комментарий можно добавить строго один файл. Это сделано для избежания partial failure (частичного успеха), когда один файл загрузился, а второй нет, что создало бы неоднозначное состояние связи document.

Надежность и State Management

Для предотвращения дублирования данных при сбоях реализована идемпотентность:

  • SQLite: Используется для хранения состояния с механизмами lease и heartbeat.
  • Replay: После рестарта клиента можно безопасно повторить операции без риска создать дубликаты тикетов.
  • Auth: OAuth с отдельными сессиями GLPI для каждого пользователя.
  • Передача данных: Bounded base64 для файлов, полное отсутствие локальных путей в API-запросах.

Качество кода и тесты

Проект выглядит зрелым с точки зрения инженерной культуры:

  • Тесты: 212 passed, 5 skipped.
  • Линтинг: Ruff и compileall проходят без ошибок.
  • Интеграции: Для тестов с реальными объектами используются opt-in переменные и ручная очистка данных, чтобы исключить утечку тестового мусора в продакшн.

Вердикт

Почему это круто: Автор не надеется на «ум» LLM, а строит забор вокруг API. Ролевая модель, явные feature-флаги и жесткая валидация MIME-типов делают этот клиент пригодным для использования в реальном энтерпрайзе, где аудит безопасности стоит выше скорости внедрения.

Где пригодится: В любой инфраструктуре, где GLPI используется как основной ITSM, а команда хочет автоматизировать первичную обработку заявок или поиск по базе знаний с помощью AI, не рискуя целостностью данных.

Подводные камни: Из-за жестких ограничений на количество и размер файлов (2 MiB) инструмент не подойдет для передачи тяжелых логов или дампов. Придется либо расширять лимиты в коде, либо использовать внешние хранилища со ссылками.
