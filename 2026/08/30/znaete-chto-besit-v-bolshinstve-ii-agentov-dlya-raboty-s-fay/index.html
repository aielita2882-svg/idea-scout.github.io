Знаете, что бесит в большинстве ИИ-агентов для работы с файлами? Что они не рабо

by

Goal-Oriented File Agent: от «болталки» к реальному редактированию кода

Большинство современных AI-агентов страдают одной проблемой: они имитируют работу с файлами, выдавая блоки кода в чат, которые пользователю приходится копировать вручную. Это не автоматизация, а дорогой интерфейс для генерации текста.

Решение — агент с прямым доступом к файловой системе и bash, который работает по принципу goal-oriented подхода: получает цель на естественном языке, планирует шаги и самостоятельно модифицирует проект.

Технический стек и архитектура

В основе лежит ChatAgent с поддержкой function calling. Вместо того чтобы ждать команду «открой файл X», агент сам решает, какие инструменты вызвать для достижения цели.

Инструментарий (Tooling)

Для взаимодействия с кодом реализован набор примитивов:

  • fs_read — чтение содержимого.
  • fs_grep — поиск по проекту.
  • fs_create — создание новых файлов.
  • fs_edit — точечное редактирование.
  • run_checks — запуск линтеров или синтаксического анализа (например, для Python) после внесения правок.

Режимы работы

Реализовано два бэкенда инструментов для разных сценариев безопасности:

  1. Direct (по умолчанию) Полноценный bash и прямой доступ к FS (аналог Claude Code).
    • По умолчанию работает в интерактивном режиме (подтверждение y/N перед каждым изменением).
    • Флаг --yes переводит агента в полностью автономный режим.
  2. MCP-режим (--mcp) Безопасный конфайнмент (sandboxing).
    • Все пути жестко ограничены директорией проекта.
    • Заблокирован доступ к .env и .git.
    • Bash-команды недоступны.
    • Флаг --dry-run позволяет получить превью изменений в формате diff без записи данных на диск.

Практическое применение

Агент эффективен в задачах, требующих анализа контекста из нескольких файлов одновременно:

  • Автоматизация документации: Генерация CHANGELOG.md на основе анализа git-истории.
  • Архитектурный анализ: Создание ADR (Architecture Decision Records), где контекст подтягивается напрямую из текущей реализации кода.
  • Рефакторинг и аудит: Поиск всех упоминаний конкретного API по всему проекту или проверка инвариантов (например, поиск захардкоженных секретов в клиентской части).

Реализация и детали

Под капотом используется модель DeepSeek. Для работы с изменениями написан кастомный diffutil, который преобразует ответы модели в читаемые git-diff. Это избавляет от «стены текста» и позволяет четко видеть, что именно меняется в коде.

Воспроизводимость подтверждена: повторный запуск с той же целью дает эквивалентный результат. Поскольку агент работает с реальными файлами, любой неудачный эксперимент откатывается стандартным git checkout.

Субъективная оценка

Почему это круто: Это переход от LLM как «собеседника» к LLM как «оператору». Возможность комбинировать fs_grep и fs_edit позволяет агенту самостоятельно исследовать незнакомый кодовый базис, не требуя от пользователя скармливать ему каждый файл по отдельности.

Где пригодится: Идеально для рутинного обновления зависимостей, миграции API во всем проекте или написания тестов под существующий функционал.

Подводные камни: Основной риск — галлюцинации при использовании fs_edit в очень больших файлах, где контекстное окно может «замылиться». Рекомендуется использовать режим --mcp с --dry-run для первичной проверки гипотез перед тем, как давать агенту полный доступ к репозиторию.

Проект полностью open-source. Код доступен в репозитории.
