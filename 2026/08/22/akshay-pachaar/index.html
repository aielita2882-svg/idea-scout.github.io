CAG vs RAG: Оптимизация контекста через Prompt Caching

Стандартный RAG (Retrieval-Augmented Generation) стал индустриальным стандартом, но у него есть проблема: избыточность. Каждый запрос в векторную БД и последующая передача одних и тех же статичных документов в контекст LLM — это лишние деньги и задержки (latency).

Решением становится CAG (Cache-Augmented Generation). Разберем, как это работает на уровне архитектуры и как внедрить в продакшн.

В чем суть проблемы RAG?

В классическом RAG схема выглядит так: Запрос -> Поиск в Vector DB -> Формирование промпта с контекстом -> Inference.

Если ваш бот отвечает по базе документации из 100 страниц, и 80% запросов касаются одних и тех же разделов, вы платите за обработку этих токенов при каждом вызове. Это неэффективно, так как данные статичны, но модель пересчитывает их каждый раз.

Что такое CAG и как он работает?

Cache-Augmented Generation переносит статичные данные из внешнего поиска непосредственно в KV-кеш (Key-Value cache) модели.

Технический бэкграунд

Внутри Transformer для каждого токена вычисляются векторы Key и Value. При генерации модель использует этот кеш, чтобы не пересчитывать предыдущие токены. Prompt Caching (реализован в API OpenAI и Anthropic) позволяет сохранять этот KV-кеш на стороне сервера. Если новый запрос начинается с точно такого же префикса, как закешированный, модель просто подтягивает готовые вычисления.

Схема гибридного подхода:

  1. CAG (Статика): Документация, API-референсы, внутренние политики. Загружаются один раз, хранятся в кеше.
  2. RAG (Динамика): Пользовательские данные, свежие логи, транзакции. Извлекаются из векторной БД «на лету».

Практические нюансы и подводные камни

Кеширование — это не «магическая кнопка», здесь есть жесткие ограничения:

  1. Строгое соответствие префикса. Кеш работает только при побайтовом совпадении начала промпта. Если вы измените хотя бы один символ в начале или поменяете документы A и B местами, произойдет cache miss, и модель пересчитает всё с нуля.
  2. Порядок имеет значение. Чтобы максимально использовать CAG, статичные данные должны идти в самом начале промпта.
    • Правильно: [Статичный контекст (Кеш)] -> [Динамический контекст (RAG)] -> [Вопрос пользователя].
  3. Окно контекста. Кеширование не увеличивает размер контекстного окна. Если забить весь лимит статикой, для динамических данных и ответа модели просто не останется места.

Вердикт: почему это круто и где использовать

CAG — это прямой путь к снижению TCO (Total Cost of Ownership) вашего AI-сервиса.

Где применять:

  • Техподдержка и Knowledge Base: когда 90% ответов базируются на одном и том же FAQ.
  • Код-ассистенты: кеширование структуры проекта или документации используемого фреймворка.
  • Юридические боты: работа с неизменными сводами законов или регламентами.

Итог: Использовать чистый RAG для всего — дорого и медленно. Использовать чистый CAG — невозможно из-за ограничений окна контекста. Оптимальный стек сегодня: CAG для фундаментальных знаний + RAG для актуальных данных. Это дает максимальный прирост скорости inference и существенно режет счета за токены.
